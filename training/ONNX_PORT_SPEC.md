# ONNX 对接规格 · 给调用方(.NET)照着实现

> 这份文档讲**怎么把一张图变成分数**, 以及**拿到分数之后怎么判**(判定规则见 §4, 四个阈值在 `vectors.json` 的 `thresholds` 块)。
> 阈值**是怎么标定出来的**属于我们内部的标定过程, 不影响你们实现, 本次不随交付。
>
> **一致性向量**: 交付包里的 `conformance/vectors.json` + `conformance/images/`。
> 分 **12 级**台阶(线路A 第 1~5 级, 线路B 第 6~11 级, **判定层第 12 级, 不用图**),
> **哪一级先对不上, 问题就在那一级** —— 先对台阶 1(纯整数, 不用图), 再往下。

## 0. ONNX 带走了什么, 你要实现什么

| | 在 ONNX 里 | 你要实现 |
|---|---|---|
| 归一化 / 通道顺序 / 放大到 256 | ✅ 已包进图 | — |
| 模型前向 | ✅ | — |
| **把图片文件解码成 RGB** | ❌ | **要 —— 见 §0.5, 这一步最容易静默走样** |
| **裁哪些小块** | ❌ | **要** |
| 金额定位 / 切块 | ❌ | **要**(线路B) |
| 元数据正则 | ❌ | 要(很简单) |
| 阈值判定 | ❌ | 要(几行 if) |

ONNX 输入 **uint8 `(N, 32, 32, 3)` NHWC RGB**, 输出 **float32 `(N,)`**, 每块一个 `ai_score`。
把归一化和放大放进图里, 是因为**通道顺序、除不除 255、双线性放大**这三样跨语言最容易写错,
而且**写错不会报错**, 只让分数偏一点 —— 而阈值就是按分数定的。

## 0.5 解码: 文件字节 -> RGB 像素(★ 2026-08-21 补, 原先漏了整整一节)

**这一节的三条, 一致性向量一条都验不出来** —— 附带那 7 张 PNG 是程序用
`Image.fromarray(数组).save()` 直接写出来的: **没有 EXIF、没有 alpha、没有调色板、不是 JPEG**。
所以**你可能 12 级台阶全绿, 却在真实进件上安静地打出另一套分数**。

### (1) ★★ EXIF Orientation: **不要旋转**

```
读图 = 直接解码, 不看 Orientation 标签, 不做任何旋转或翻转
```

**理由**: 我们的阈值就是在"不旋转"的口径下标定的 —— 打分入口 `ssp_score_one.py` 那一句
`Image.open(p).convert("RGB")` **没有** `exif_transpose`, 标定脚本同样没有。

> ⚠ 你会在交付的 `locate_blue.py` 里看到一处 `ImageOps.exif_transpose(...)` ——
> 那在它自己的**命令行可视化入口 `main()`** 里, **打分这条路不经过它**。
> 打分走的是 `locate_amount_auto(rgb)`, 收的已经是解好的数组。**以打分入口为准: 不旋转。**

**★ .NET 这边要特别当心**: **ImageSharp 的 `Image.Load` 默认会按 Orientation 自动摆正**,
GDI+ / SkiaSharp / WIC 默认不摆。**用 ImageSharp 就必须显式关掉自动摆正。**

**不关掉会怎样**: Orientation = 5~8 的图 **宽高会对调**, 于是
`y = next() % (H-32+1)` 和 `x = next() % (W-32+1)` 的上界全变 ->
**从台阶 2 起每一个坐标都不同** -> 取到的 16 块完全是另一批 -> 线路A 换一套分数。
线路B 的金额带 `y ∈ [0.05H, 0.45H]` 也会落到错的内容上, 退化成"定位失败"分支。

**谁会带 Orientation**: 手机相机拍出来的图(**翻拍件 Orientation=6/8 极常见**)。
纯截图一般不带, 所以**平时看不出来, 只在翻拍件上出事**。

### (2) alpha / 调色板 / 灰度 / CMYK 怎么转 RGB

按 **PIL `convert("RGB")` 的语义**, 它和 .NET 常见库的默认行为**不一样**:

| 输入 | 我们的口径 | .NET 库常见默认 |
|---|---|---|
| RGBA / LA | **直接丢掉 alpha 通道** | 合成到白底(或黑底) |
| 半透明像素 | **不做 unpremultiply** | 可能会做 |
| P(调色板) | 查表展开 | 一般一致 |
| L(灰度) | 灰度值复制到三通道 | 一般一致 |

**"丢 alpha"和"合成到白底"给出的像素完全不同** -> 纹理能量不同 ->
64 个候选里谁最大直接换人 -> 分数不是差 1e-4, 是换了一套。
手机截图和修图 App 存出来的 PNG 带 alpha 的**不在少数**。

### (3) ★ JPEG: 台阶 1~3 的"完全相等"**只对附带那 7 张 PNG 成立**

PNG 是无损的, 任何解码器出来的像素逐位相同, 所以台阶 1~3 可以要求完全相等。
**JPEG 不是** —— 不同解码器(libjpeg-turbo / .NET 自带 / ImageSharp)在 IDCT 和上采样上
允许有 **±1 的像素级差异**, 这是 JPEG 标准允许的, 不是谁写错了。

后果不止台阶 3:
- **线路A(台阶 2~3)**: 两个候选块能量咬得很近时, `>=` 的并列规则可能选到**另一块**。
- **线路B(台阶 7~9)**: 定位靠的是 `gray < 140` 这种**硬整数阈值**加连通域,
  像素差 ±1 足以让边缘像素跨过阈值 -> 连通域形状变 -> **定位框和切块坐标跟着变**。

所以 JPEG 上**整数那几级都可能对不上**, 不只是取块那一级。

**我们没有量过这件事有多频繁 —— 这里如实说明, 不编数。**

**建议的做法**:
1. 先用附带的 7 张 PNG 把台阶 1~12 全部对齐(整数那几级必须完全相等, 浮点那几级按 1e-4 收, 见 §5)
2. 再拿**一批真实 JPEG 进件**, 两边各跑一次, 比对 `final_ai_score`
3. 如果只有极少数图的分数有肉眼可见的差, 且都不跨阈值 -> 可以接受
4. **如果有图跨了阈值, 告诉我们**, 我们这边用同一批图复现

真实进件以 JPEG 为主, **所以第 2 步不能省** —— 只对 PNG 向量就签字, 等于没验过主要场景。

## 0.6 五条"写错不报错"的细节(★ 2026-08-21 补, 都是向量验不出来的)

### (1) ★★ 并列规则: **两条线是相反的**, 千万别照搬

| | 取哪个 | 代码依据 |
|---|---|---|
| **线路A** 64 个候选取能量最大 | **并列取最后一个** | `if best_e is None or e >= best_e`(`>=` 所以后来者覆盖) |
| **线路B** 块内取最富纹理窗口 | **并列取第一个** | `np.argmax` 返回**首个**最大值(行优先) |

**这两条正好相反。** 规格上一版在 `vectors.json` 里把线路B 写成"规则同线路A", **那是错的, 已更正。**
纯色/大片平坦区域并列极常见, 写反了就会稳定选到另一个窗口。

### (2) 白图定位的灰度公式: **必须是 BT.601**

```
gray = 0.299*R + 0.587*G + 0.114*B      (OpenCV COLOR_RGB2GRAY, 定点四舍五入)
```

`gray < 140` 是白图定位的**唯一判据**, 而不同库的默认灰度公式不一样 ——
BT.709 是 `0.2126R + 0.7152G + 0.0722B`, 蓝色权重差了快一半。
支付宝蓝底在 601 下约 `gray=106`(所以蓝图要走另一个定位器);
换成 709 这个值会变, `< 140` 的判定跟着变, **连通域、行聚类、定位框全变**。

### (3) 积分图累加**不能用 float32**

线路B 找最富纹理窗口用的是积分图。**用 float64 或 int64 累加。**
Python 那边是白捡的(`cv2.integral` 对 float32 输入默认输出 CV_64F),
.NET 手写时若用 float32, **真实尺寸的高纹理块积分和会超过 2^24**
(float32 能精确表示整数的上限), 于是窗口选错。
**7 张对照图太小太干净, 42 个块一个都触发不到 —— 这条向量验不出来。**

### (4) 块不足 32 时的放大: 口径写死

```
s      = max(32/h, 32/w)
目标宽 = max(32, int(w*s + 0.5))        ★ int(x+0.5) = 四舍五入, 不是银行家舍入
目标高 = max(32, int(h*s + 0.5))
插值   = 双线性, **半像素中心对齐**  src = (dst + 0.5) * scale - 0.5
```

结果**可以不是正方形**。用 OpenCV 绑定的话 `INTER_LINEAR` 天然就是这个口径。

### (5) 种子的链路约束: crc32 必须算**进件那一份原始字节**

```
seed = crc32(整个文件的原始字节) & 0x7FFFFFFF ; 为 0 则取 1
```

**三条硬约束**:
1. 算 crc32 的字节, 必须和送进解码器的**是同一份**
2. **打分之前不许重新编码**(不许转存、不许改质量、不许缩放后再存)
3. 服务若在入口处做过任何"标准化"(比如统一转 JPEG), **crc32 必须在那之前算**

否则种子变 -> 取的 16 块全变 -> 线路A 换一套分数。**而且不会报错。**

## 0.7 三条部署与接口约定

### (1) ★★ 线程数**必须显式设**, 否则多进程会互相抢核

`InferenceSession` 不传 `SessionOptions` 时, onnxruntime **按 CPU 核数开 intra-op 线程** ——
每个进程都以为自己独占整台机器。**多进程部署时 N 个进程 x M 个核 = 严重超订。**

2026-08-21 实测(**24 物理核**开发机, 每档 60 张真实进件, 取中位):

| 每进程线程数 | 单张耗时 | 相对 1 线程的加速比 |
|---|---|---|
| 1 | 4.072 秒 | 1.00 |
| **2** | **1.963 秒** | **2.07** |
| 4 | 1.129 秒 | 3.61 |
| 8 | 1.020 秒 | 3.99 |
| 16 | 1.105 秒 | 3.68 ← **比 8 线程还慢** |

**2 线程这一档是满效率**(2.07 倍), **4 以上收益急剧衰减, 16 反而倒退。**

#### 怎么选: 按"总吞吐 = (核数 / 每进程线程数) x (1 / 单张耗时)"算

以 **48 核**一台为例:

| 每进程线程 | 可开进程数 | 单张耗时 | 整机 张/秒 | 每进程内存 x 进程数 |
|---|---|---|---|---|
| 1 | 48 | 4.07 秒 | 11.8 | 48 GB |
| **★ 2(推荐)** | **24** | **1.96 秒** | **12.2** | **24 GB** |
| 4 | 12 | 1.13 秒 | 10.6 | 12 GB |
| 8 | 6 | 1.02 秒 | 5.9 | 6 GB |

**每进程 2 线程是整机总吞吐最高的一档**, 而且延迟只有 1 线程的一半、内存也只要一半。

★ 但**它不是延迟最低的一档** —— 4 线程 1.13 秒、8 线程 1.02 秒都比它的 1.96 秒快。
单张延迟要压到 1.2 秒以内就选 4 线程, 代价是整机总吞吐掉约 13%(12.2 -> 10.6 张/秒)。
**吞吐和延迟在这里是此消彼长的, 不存在一档全占。**

> ⚠ **不要照搬"每进程 1 线程总吞吐最高"这种说法** —— 那只在**并行效率次线性**时成立,
> 而这个模型在 2 线程档是满效率, 所以 1 线程白白多付一倍延迟却换不来吞吐。
> (本节上一版就是这么写错的, 已按实测更正。)

> ⚠ 上表是**单进程实测**外推的, 没有计入 24 个进程同时跑时争抢 L3 和内存带宽,
> 实际整机吞吐会**略低于**表中数字。

**无论选哪个, 都要显式设**, 不能沿用默认:

```csharp
var so = new SessionOptions();
so.IntraOpNumThreads = 2;      // 按上表取舍, 不要留默认
so.InterOpNumThreads = 1;
```

### (2) `.jpeg` 免自动拒 —— "扩展名"到底取哪个字符串?

规则本身在 §4。这里定的是**输入从哪儿来**, 交付上一版没写:

- **取原始上传文件名的扩展名**, 不是 OSS 存储 key, 不是内部重命名后的名字
- 大小写不敏感, 去掉前后空白后比较
- **取不到文件名时, 按"不是 `.jpeg`"处理**(即照常可以自动拒)

**为什么要写死**: 拿不到原始文件名 -> 豁免永远不触发 -> 自动拒率会顶到 2.7/万 以上,
而 2.7/万 正是在"已免自动拒"的前提下标定的。
**反过来**, 若取的是攻击者能控制的上传表单文件名, 这条豁免就变成一个
**任意可触发的降级开关** —— 改个名就能把自己从自动拒挪进人工队列。两边都要有意识。

### (3) 参照实现的 stdout **不是纯 JSON**

`ssp_score_one.py` 第一次跑会往 **stdout** 打一行
`(没找到配置, 已写一份默认的到 ...)`, 之后才是 JSON。汇总走 stderr。

-> **逐行严格 parse 会在第一次运行就炸。** 要么容忍非 JSON 行(跳过不以 `{` 开头的行),
要么先跑一次让配置落盘再正式对数。**这只是参照实现的行为, 不是要求你们的服务也这样。**

## 1. 线路A · 整图 AI 生成

### 1.1 种子

```
seed = crc32(整个文件的字节) & 0x7FFFFFFF
if seed == 0: seed = 1          # xorshift32 不能从 0 开始
```
**用文件字节, 不用文件名** —— 否则改个名就能重新抽一次奖(实测同图不同抽样, 阈值附近判定不一致率 46.9%)。

### 1.2 随机数发生器 xorshift32

```
state ^= state << 13
state ^= state >> 17
state ^= state << 5
返回 state              # 全程 uint32, 每步都要掩回 32 位
```
自检: `xorshift32(1) == 270369`。

### 1.3 坐标

每块两个数, **先 y 后 x**(顺序反了取到的块完全不同):
```
y = next() % (H - 32 + 1)
x = next() % (W - 32 + 1)
```

### 1.4 选块

每轮取 **64** 块, 算纹理能量, **取能量最大的那一块**。

> ★★ **是最大, 不是最小。** SSP 原版是 `sort(升序)` 后取 `patch_list[-1]`。
> 我们第一版按"最小"写, 结果 597 张图分数**中位涨了 0.16, 97.7% 一边倒** ——
> 这是本项目在这一步付过的代价。
>
> ★ **并列取最后出现的那个**(升序稳定排序取 `[-1]` 的等价语义)。
> 收据图有大片纯色, **能量并列是常态**, 这条不写死两边必然选到不同的块。
> 实现上用 `>=` 一路覆盖, 用 `>` 会停在第一个。

**纹理能量**(与 SSP `compute()` 逐字一致, int64 累加):
```
E = Σ|p[y][x] - p[y][x+1]|      水平
  + Σ|p[y][x] - p[y+1][x]|      垂直
  + Σ|p[y][x] - p[y+1][x+1]|    主对角
  + Σ|p[y+1][x] - p[y][x+1]|    副对角
三个通道分别算再相加
```

### 1.5 汇总

上面重复 **16** 轮 -> 16 块 -> 一次喂进 ONNX -> **16 个分数求平均** = `final_ai_score`。

> **`repeat=16` 和 `64` 块都不能改。** 改了分数就变, 阈值当场作废。

## 2. 线路B · 局部改金额

线路B **没有随机数**, 全程确定性 —— 所以不需要 PRNG, 但几何和定位要一模一样。

### 2.1 版式判定

```
取图像**上三分之一**, 算 R/G/B 三个通道的均值
是蓝图 ⟺ B > R + 25 且 B > G + 15
```

### 2.2 金额定位 · 蓝图(白字蓝底)

```
带状区域 y ∈ [0.05H, 0.45H]
近白掩码: min(R,G,B) > 175 且 max-min < 45
connectedComponentsWithStats(掩码, 8 连通)
逐个连通域过滤, 保留满足: 0.025H ≤ 高 ≤ 0.12H, 面积 ≥ 30, 宽 ≤ 0.5W
若无 -> 定位失败
maxh = 最大高度; 只留 高 ≥ 0.6*maxh 的块
若剩余 < 2 个 -> 失败
cy = 这些块竖直中心的**中位数**; 剔掉 |中心 - cy| ≥ 0.6*maxh 的
若剩余 < 2 个 -> 失败
框 = 这些块的外接矩形; 若 宽 < 0.08W -> 失败
```

### 2.3 金额定位 · 白图(浅底深字)

```
灰度化 (RGB -> GRAY)
带状区域 y ∈ [0.08H, 0.55H]
深色掩码: gray < 140      ★ 灰度公式**见 §0.6(2)**(BT.601), 不是随便哪种灰度都行
connectedComponentsWithStats(掩码, 8 连通)
过滤保留: 0.02H ≤ 高 ≤ 0.22H, 面积 ≥ 20, 宽 ≤ 0.5W
按**同一行**聚类(见下), 只看 ≥2 个块 且 横跨 ≥ 0.1W 的行
在这些行里取**中位高度最大**的那一行; 框 = 该行的外接矩形
```

> ★★ **"中位高度"是上中位数, 不是标准中位数** —— 这里**不取平均**:
>
> ```
> 把该行所有块的高度**升序排**, 取下标 len // 2 那一个
> med = sorted(heights)[len(heights) // 2]
> ```
>
> 偶数个块时它取的是**中间偏大**的那一个, 而**不是**中间两个的平均。
> 例: 高度 `[10, 20, 30, 40]` -> **30**(标准中位数会给 25)。
> 结果**永远是某个块的真实高度(整数)**, 不会出现 `.5`。
>
> **写成标准中位数会怎样**: 块数为偶数的行算出来的值不同 -> 选中的行可能换一行 ->
> 定位框换地方 -> 线路B 整条换一套分数。**而且不报错。**
>
> ⚠ 注意**蓝图那条走的是另一种**: `§2.2` 里用的是标准中位数(`np.median`, 会取平均、可能带小数),
> 而且算的是**中心 y**不是高度。**两条别混用。**

**同一行聚类**(按 y 升序遍历, 逐个塞进已有行或新开一行):
```
块 c 与行 r 同行 ⟺ 竖直重叠 ≥ 0.5 * min(c.高, r.高)
   竖直重叠 = min(c.y+c.高, r.y1) - max(c.y, r.y0)
```
> **为什么按行聚类而不是"取最高的连通域"**: 账单页顶部的**商家头像**(约 125~138px)
> 比金额数字(71~78px)还高, 会把金额挤掉。实测定位率因此从 73.0% 提到 **98.0%**。

### 2.4 裁剪与切块

```
定位成功 -> 裁到金额框, **四边各外扩 pad 像素**, 然后切 **2 列 x 2 行**
             pad = int(max(8, 框高 * amount_pad))
             ★ amount_pad = 0, 但那个 max(8, ...) 是**下限** -> **pad 实际是 8, 不是 0**
             ★ 定位成功时是 **2x2**, 不是 3x6("区域已经很小, 切少量块就够")
定位失败 -> **不出信号**(是"无意见", 不是"判真"), 但仍按 roi-top 0.6 保留上部继续算,
             并切 **3 列 x 6 行**
相邻块按 0.15 重叠(cols/rows 用上面那两种情形对应的值):
    tw = w/cols, th = h/rows, ox = tw*0.15, oy = th*0.15
    x0 = max(0, floor(c*tw - ox)),  x1 = min(w, floor((c+1)*tw + ox))
    y0 = max(0, floor(r*th - oy)),  y1 = min(h, floor((r+1)*th + oy))
    丢掉 宽<8 或 高<8 的块
```

### 2.5 每块取"纹理最丰富"的 32x32 窗口

**穷举所有窗口取最大, 不是随机取样**(积分图一次算完):
```
块太小(< 32) -> 双线性放大到至少 32
每像素纹理强度 t(float32), 四个方向的差**各自累加到那一对像素里左上角那一个**:
  t[y][x] += |p[y][x]   - p[y][x+1]|     水平   (最后一列不加)
  t[y][x] += |p[y][x]   - p[y+1][x]|     垂直   (最后一行不加)
  t[y][x] += |p[y][x]   - p[y+1][x+1]|   主对角 (最后一行和最后一列都不加)
  t[y][x] += |p[y+1][x] - p[y][x+1]|     副对角 (同上)
三个通道分别算再相加。★ **不要写成居中、也不要两个像素各加一半** —— 边界那一圈会不一样。
对 t 做积分图, 求所有 32x32 窗口的和, 取**最大**的那个窗口
并列取**第一个**(argmax 的语义)
```

> ★ 注意这里的并列规则和线路A **相反**(线路A 取最后一个, 这里取第一个) ——
> 两边分别对应 `sort()[-1]` 和 `argmax()` 的原生语义, 不要统一。

### 2.6 汇总

每块的 32x32 窗口喂 ONNX -> 每块一个分 -> **取前三高的平均** = `tile_top3`。

## 5. 一致性向量怎么用

`vectors.json` 每个用例给**两条线各自的台阶**:

**线路A**

| 台阶 | 字段 | 容差 |
|---|---|---|
| 1 | `stage1_xorshift_first8` | **完全相等**(不用图, 先对这个) |
| 2 | `stage2_round0_positions` | 完全相等 |
| 3 | `stage3_chosen_positions` / `_energies` | 完全相等 |
| 4 | `stage4_patch_scores` | 1e-4 |
| 5 | `stage5_ai_score` | 1e-4 |

**线路B**(给了 `--b-onnx` 才有)

| 台阶 | 字段 | 容差 |
|---|---|---|
| 6 | `stage6_page` (`white`/`blue`) | 完全相等 |
| 7 | `stage7_locate_box` (定位框, 定不到为 `null`) | 完全相等 |
| 8 | `stage8_crop_box_after_pad` / `stage8_tile_grid` | 完全相等 |
| 9 | `stage9_tiles` (每块在裁剪图里的坐标) | 完全相等 |
| 10 | `stage10_tile_scores` | 1e-4 |
| 11 | `stage11_tile_top3` | 1e-4 |

> ★ 台阶 8 尤其要对: `crop_box` 能验出 **pad 是不是 8**, `tile_grid` 能验出
> **定位成功时是不是 2x2**。这两处正是我们自己写错过的地方 —— 光对最后的分数看不出来。
>
> 用例里 **case1~6 是"定位成功"分支(2x2, 4 块), case7 是"定位失败"分支(3x6, 18 块)** ——
> **两条分支都要跑通**, 只对上一条不算数。

**判定层**(★ **不用图**, 无论传没传 `--b-onnx` 都会生成)

| 台阶 | 字段 | 容差 |
|---|---|---|
| 12 | `decision_cases[].expected_decision` / `expected_reason` | **完全相等**(字符串) |

> `decision_cases` 是 **20 条真值表**, 输入是五元组
> **(A分, B分, B是否定位到, 扩展名, 线路C铁证)**, 直接喂你们的判定函数比对即可, **不需要图**。
> 阈值取本文件 `thresholds` 块。
>
> ★ **它覆盖的正是那 7 张 PNG 走不到的分支** —— 合成图没有 AIGC 元数据(线路C 永远空),
> 而且**全是 `.png`**(`.jpeg` 免自动拒永远不触发)。**只对到台阶 11 的话, 判定规则一条都没被验过。**
> 重点四条: `>=` 是**闭区间**(分数**等于**严格线就该拒) / 线路B **没定位到就不出信号**(哪怕 0.9999) /
> **线路C 命中会短路**(`.jpeg` 免拒**管不到它**) / `.jpg` **不等于** `.jpeg`。

**台阶 1~3、6~9、12 是整数或字符串, 差一个就是错。台阶 4/5/10/11 是浮点, 容差 1e-4。**

> ★★ **1e-4 这个数的前提是: 你们和我们都在 CPU ExecutionProvider 上跑。**
> 它的来历是 **ONNX 自身的浮点差约 1e-6, 留两个数量级余量**, 与"跨设备差异"无关。
>
> **换 GPU 或别的 EP 就不要用 1e-4 收** —— 我们实测跨设备(CPU vs GPU)在**高分图**上
> 中位 **2.8e-4** / p95 **2.4e-3** / 最大 **1.2e-2**, **比这个闸门还大**,
> 会在没有真 bug 的情况下飘红。真要跨设备比, 改看**低分图**(分数 < 0.05)的中位差 < 1e-5
> 来判预处理喂对没有, 高分图另行核对。

> ★ **直接用附带的那七张 PNG, 不要自己重新生成。**
> 种子是 `crc32(整个文件字节)` —— 换个 PNG 编码器(甚至换个版本)压出来的字节可能不同,
> 种子就变了, 向量全部对不上。七张一共也就几十 KB, 直接拷过去用。
>
> 用例覆盖: 白底文字 / 蓝底渐变(考验**蓝图**那条定位路径) / 大片纯色(考验"并列取最后一个") /
> 密集文字 / 窄长图(考验坐标范围) / **1080x2400 真实尺寸** /
> **不画金额行(考验"定位失败"那条分支)**。

## 6. 不能动的东西

改这些**任意一样**, 阈值全部作废, 而且**不会报错**:

- `repeat = 16`、每轮 `64` 块、块大小 `32`
- 取块方向(**最大**)与并列规则(线路A 最后一个 / 线路B 第一个)
- 切块(**定位成功 `2x2` / 失败 `3x6`**)、重叠 `0.15`、`roi-top 0.6`、
  `amount-pad 0`(-> 实际外扩 **8 像素**)、聚合 `top3`

  > ★ `roi-top 0.6` 和 `agg top3` 是 `ssp_config.json` 的 `line_b.flags` **显式传进去的**,
  > 而 `predict_tiled.py` 自己的默认值是 `roi-top 1.0` / `agg max`。
  > **不带这些参数直接跑那个脚本会得到另一套分数** —— 照这份规格实现时,
  > 要用的是上面这组值, 不是脚本默认值。
- 两个定位器里的任何一个阈值(175/45/140/0.5/0.6 等)

> ★★ **还有一条在代码之外**: 服务器上 `SSP/utils/patch.py` 的 `patch_list[-1]` 是**改过的**,
> 原始开源版本是 `[0]`。那个仓库不在我们的版本控制里 ——
> **重装/更新/重新 clone 之后, 第一件事是确认这一行还是 `[-1]`。**
> 变回去的话所有分数和阈值当场作废, 而且**只会安静地给出另一套数**。
