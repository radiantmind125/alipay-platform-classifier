# 预登记 · 对真实环境误杀率的预测

> **写于 2026-08-21, 在经理开始记录真实数据之前。**
>
> 这份文档的**全部价值在于它的日期**。等真实数字出来之后再写同样的内容, 那不叫预测, 叫找补。
> 提交历史就是时间戳, **不要事后修改这里的预测值** —— 要修正就在文末追加, 保留原值。

## 一句话

我们预测经理那边记出来的是 **自动拒 每万张 2.7 张, 转人工 每万张 17.4 张**。

## 这两个数是怎么来的

| 项 | 值 |
|---|---|
| 测量池 | **88,645 张**(重搭的 90,377 张排除后的**验收池**, 不是标定池) |
| 取块 | `patch_mode: lcg` |
| 阈值 | `0.8031 / 0.6497 / 0.9811 / 0.7549` |
| 自动拒 | **24 张** = 2.7/万 |
| 转人工 | **154 张** = 17.4/万 |
| `.jpeg` | **已免自动拒**(移出自动拒适用人群) |

## ★ 成立前提(任何一条不成立, 预测作废)

1. **`.jpeg` 结尾的图不自动拒, 一律转人工。**
   阈值就是在这个前提下标的。不实现这条, 自动拒率**必然高于 2.7/万**。
2. **翻拍走别的通道。** 我们的池子里翻拍是被 `screenshot_filter` 挑走的(1,277 张)。
   翻拍若混进同一条流, 误杀会高于 2.7/万 —— **这一条至今没有得到确认**。
3. 进件的**图片来源和压缩管线**和我们的池子大体一致。

## 偏离了说明什么

| 观察到的 | 最可能的原因 | 怎么查 |
|---|---|---|
| **自动拒明显偏高** | `.jpeg` 那条没实现 | 把他们的自动拒按扩展名分组, 看 `.jpeg` 占比是不是异常高 |
| 同上 | 翻拍混进来了 | 抽查自动拒的图, 看有没有相机 EXIF / 摩尔纹 |
| 同上 | 实现有出入 | 跑一致性向量, 看第几级台阶先对不上 |
| **转人工明显偏高** | 同上三条, 只是阈值更松所以更早暴露 | 同上 |
| **两个数都接近 0** | ★ **不是好消息, 大概率是实现坏了** | 见下 |
| 自动拒偏低但转人工正常 | 可能只是进件更干净 | 先别动阈值, 多攒几天 |

### ★★ "误杀率特别低"是红旗, 不是捷报

模型没跑起来、输入喂错、分数恒定在低位 —— 这些都会让误杀率**好看得离谱**。
**唯一的判别方法是反向对照**: 拿一张已知的 AI 假图过他们的实现。

已知样本: `s3_voucher_GWCZ2086494312195076096_20260810004922.png`
预期 **自动拒**, 线路A ≈ **0.99176**, 线路B ≈ **0.999833**, 厂商认出 **OpenAI gpt-image**。

**误杀率低 + 这张图也放行 = 实现坏了, 不是效果好。**

## 要记多少张, 这个数才算得上数

我们的数自带抽样噪声。按泊松:

| 指标 | 我们的观测 | 95% 区间(在我们池子上) |
|---|---|---|
| 自动拒 | 24 张 / 88,645 | 约 **1.6 ~ 3.8 /万** |
| 转人工 | 154 张 / 88,645 | 约 **14.6 ~ 20.2 /万** |

对他那边同理 —— **要看到约 25 次事件, 比率才有 ±20% 的精度**:

- **转人工** 17.4/万 -> 约 **1.4 万张**就够 -> 按日均 3~4 万, **半天**
- **自动拒** 2.7/万 -> 约 **9.3 万张**才够 -> **大约 3 天**

**所以: 第一天的自动拒率不用当真。** 一天只有 8~11 次事件, 波动天然就很大,
看到 0 或者看到 20 都不奇怪。**至少攒三天再谈这个数。**

## 明确不预测的东西

**漏杀率。** 端到端从来没量过。这份文档只对**误杀**做预测,
任何把这里的数字当成"检出率"引用的说法都是误读。
